# T04: TypeScript output slimming

- **Priority:** P0
- **Size:** Large
- **Depends on:** [T01](./T01-data-first-runtime-architecture.md), [T02](./T02-compact-parser-plan-format.md)
- **Suggested PR title:** `Slim generated TypeScript output to adapters and optional types`

[Back to index](./README.md)

## Objective

Make generated TypeScript small. A generated parser should not check in hundreds of kilobytes of lexer/parser implementation. It should contain parser-plan data, optional types, and a tiny adapter around the shared runtime.

## Problem

Generated TypeScript output currently has too many responsibilities:

```text
syntax types
DFA transition data
DFA scanning logic
LR tables
parser driver logic
branch search
reducer VM
CST construction
source maps
token-stream validation
public adapters
```

Only some of that is grammar-specific. Most of it should live once in the package runtime.

## Required work

### 1. Split generated TypeScript into data, types, and adapter

Preferred default output:

```text
typescript/
  plan.ts       # compact grammar data only
  types.ts      # optional generated CST/token types
  mod.ts        # tiny adapter and reexports
```

Remove default output files such as:

```text
lexer.ts
parser.ts
syntax.ts
```

unless they are tiny compatibility wrappers.

### 2. Add type emission modes

Generated structural types are useful but can be large.

Add:

```text
--emit-types none
--emit-types minimal
--emit-types full
```

Suggested behavior:

- `none`: no generated node interfaces;
- `minimal`: export token/rule name unions and generic aliases;
- `full`: current detailed field-specific interfaces.

Default should be `minimal` unless compatibility requires `full` for one release.

### 3. Use generic runtime node types by default

Shared runtime can expose generic types:

```ts
interface RuleNode {
  readonly kind: "rule";
  readonly ruleId: number;
  readonly name: string;
  readonly span: Span;
  readonly children?: readonly SyntaxElement[];
  readonly fields?: FieldMap;
}
```

Generated minimal types can add names:

```ts
export type RuleName = "module" | "decl" | "expr";
export type TokenName = "IDENT" | "INT" | "WS";
```

Full field-specific types should be optional because they increase generated bytes and TypeScript checker cost.

### 4. Generate tiny adapter functions

A generated `mod.ts` should look conceptually like:

```ts
import { createParser } from "@mewhhaha/baba/runtime";
import { parserPlan } from "./plan.ts";

const parser = createParser(parserPlan);

export const lex = parser.lex;
export const parse = parser.parse;
export const parseTokens = parser.parseTokens;
export const parseTokensUnchecked = parser.parseTokensUnchecked;
```

Avoid copying runtime helper functions into generated output.

### 5. Move source map utilities to shared runtime

Utilities such as `positionAt` and `createSourceMap` are not grammar-specific. Export them from the shared runtime and reexport them from generated adapters.

### 6. Move token-stream validation to shared runtime

Token-stream validation depends on the plan data but not on generated source. The shared runtime should own it.

### 7. Make generated imports configurable

Generated adapters should support:

```text
--runtime-import @mewhhaha/baba/runtime
--runtime-import ../vendor/baba-runtime.ts
```

This allows users to vendor the runtime if needed without copying a generated runtime per grammar.

### 8. Keep compatibility temporarily

For users depending on file names, emit compatibility wrappers when requested:

```sh
--compat-files lexer.ts,parser.ts,syntax.ts
```

These files should only reexport shared runtime functions, not contain implementation.

Example:

```ts
export { lex } from "./mod.ts";
```

### 9. Add generated byte budgets

For representative grammars, default TypeScript output should fit strict budgets.

Example target budgets:

```text
tiny grammar: under 10 KB excluding plan
large-runtime grammar: under 50 KB excluding plan and full types
```

Full types can have a separate budget.

## Bad generated output

```ts
function scanOneToken(...) { ... }
function parseTokenList(...) { ... }
function reduceProduction(...) { ... }
```

in every generated grammar.

## Good generated output

```ts
import { createParser } from "@mewhhaha/baba/runtime";
import { parserPlan } from "./plan.ts";
export const parser = createParser(parserPlan);
export const parse = parser.parse;
```

## Tests

1. default generated TypeScript contains no parser driver implementation;
2. adapter imports shared runtime;
3. `--emit-types none` emits no type file;
4. `--emit-types minimal` emits small unions/generic aliases;
5. `--emit-types full` preserves detailed field types;
6. compatibility files are wrappers only;
7. Deno/Node/Bun smoke works;
8. two generated grammars share the runtime import;
9. generated byte budgets pass;
10. full-type generation remains deterministic.

## Acceptance criteria

- TypeScript target default output is tiny adapter + plan + minimal types.
- Runtime algorithms are not emitted per grammar.
- Public `lex`/`parse` convenience exports still work.
- Optional full typing remains available.
- Large-runtime fixture TypeScript bytes drop materially from T00 baseline.

## Out of scope

- Wasm architecture; see T03;
- compact plan binary; see T02;
- CST laziness; see T05;
- changing parser semantics.
