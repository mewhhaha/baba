# T07: Conflict runtime splitting

- **Priority:** P1
- **Size:** Medium/Large
- **Depends on:** [T01](./T01-data-first-runtime-architecture.md)
- **Suggested PR title:** `Keep branch-search runtime out of deterministic parsers`

[Back to index](./README.md)

## Objective

Make deterministic grammars use a small deterministic runtime, and make ambiguous/branch-search machinery opt-in and isolated.

## Problem

Branch search is useful for some grammars, but it is expensive in code size, plan size, mental model, testing surface, and runtime overhead. Deterministic grammars should not pay for:

- branch queues;
- branch cloning;
- trace growth;
- ambiguity detection;
- best-failure merging;
- multiple-success policy;
- branch-specific diagnostics;
- conflict metadata payloads.

Even if branch code is conditionally emitted today, a shared runtime can accidentally reintroduce it into every parser unless split deliberately.

## Required work

### 1. Split runtime profiles

Define runtime profiles:

```text
deterministic      one action per state/terminal
branching          declared conflicts only
legacy             compatibility behavior if needed
```

Parser plan should declare:

```ts
conflictProfile: "deterministic" | "branching";
```

### 2. Emit/load only required profile

For TypeScript shared runtime:

```ts
import { createDeterministicParser } from "@mewhhaha/baba/runtime/deterministic";
```

For branching grammars:

```ts
import { createBranchingParser } from "@mewhhaha/baba/runtime/branching";
```

Do not import branching runtime from deterministic generated adapters.

For Wasm, use either:

- separate generic deterministic and branching executors; or
- one executor with sections/features that can be excluded by packaging.

Measure which is smaller.

### 3. Store deterministic tables differently

Deterministic action rows do not need action sets.

Instead of:

```json
{ "terminal": 5, "actions": [{ "kind": "shift", "state": 12 }] }
```

use:

```text
terminal=5, actionKind=SHIFT, payload=12
```

Only branching profile needs action sets.

### 4. Move ambiguity metadata out of deterministic plans

For deterministic plans, omit:

- conflict IDs;
- branch groups;
- ambiguity mode defaults;
- max branch limits;
- trace branch metadata;
- multiple-action rows.

### 5. Make branching opt-in and explicit

If a grammar has conflicts:

- deterministic target should fail with a clear conflict diagnostic;
- branching parser should be enabled only by metadata or explicit CLI/API flag;
- generated output should say it uses branching runtime.

Example:

```json
{
  "version": 2,
  "parser": {
    "conflicts": [{ "conflict": "c_..." }]
  }
}
```

### 6. Put branch limits in branching only

Deterministic parsers should not carry options like:

```text
maxExploredBranches
maxQueuedBranches
ambiguityMode
```

unless they are using the branching runtime.

### 7. Add a diagnostic when users choose too much runtime

If a user requests branching runtime for a deterministic grammar:

```text
BRANCH_RUNTIME_UNUSED
This grammar has no declared parser conflicts. Use deterministic runtime for smaller output and faster startup.
```

### 8. Add benchmarks

Compare deterministic and branching output for the same grammar where possible:

```text
generated bytes
plan bytes
import time
first parse time
hot parse time
```

### 9. Keep Tree-sitter separate

Tree-sitter conflicts do not automatically mean the portable runtime must branch. Portable runtime conflicts should remain under parser metadata.

## Examples

### Deterministic grammar

```ebnf
token INT = /[0-9]+/ ;
skip WS = /[ \t\r\n]+/ ;
module = expr ;
expr = INT ("+" INT)* ;
```

Should use deterministic runtime only.

### Branching grammar

```ebnf
token ID = /[A-Za-z_][A-Za-z0-9_]*/ ;
skip WS = /[ \t\r\n]+/ ;
module = primary ;
primary = tuple | group | atom ;
tuple = "(" atom "," atom ")" ;
group = "(" atom ")" ;
atom = ID | "(" primary ")" ;
```

Should fail in deterministic mode until a declared conflict enables branching.

## Tests

1. deterministic grammar imports no branching runtime;
2. deterministic plan has no action sets;
3. deterministic parse works;
4. conflicting grammar fails without metadata;
5. conflicting grammar uses branching runtime with metadata;
6. branch limits exist only in branching parser options;
7. unused branching runtime warning;
8. TypeScript/Wasm parity for deterministic and branching profiles;
9. generated bytes for deterministic profile are smaller;
10. cold-start benchmark separates deterministic vs branching.

## Acceptance criteria

- Deterministic parsers do not carry branch-search code or data.
- Branching runtime is opt-in and visibly selected.
- Deterministic plan encoding is smaller than branching plan encoding.
- Default small grammars use deterministic runtime.
- Conflict behavior remains correct and bounded.

## Out of scope

- new conflict-resolution semantics;
- GLR parse forests;
- error recovery;
- contextual lexing changes.
