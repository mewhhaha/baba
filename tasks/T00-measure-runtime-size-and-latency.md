# T00: Measure runtime size and latency

- **Priority:** P0
- **Size:** Medium
- **Depends on:** none
- **Suggested PR title:** `Add runtime size and cold-start benchmark gates`

[Back to index](./README.md)

## Objective

Create a reproducible benchmark and size-reporting suite that captures the current failure mode:

- roughly 500 KB of Wasm bytes for one grammar;
- around 6 seconds to instantiate;
- around 30 ms to parse a small file.

This task does not optimize anything. It makes the problem measurable and prevents future agents from guessing.

## Problem

The current benchmark coverage is not enough to guide the architectural fix. A normal benchmark may measure hot parse loops after everything is already compiled, instantiated, and cached. That hides the actual user pain:

```text
generate parser
import generated files
compile/instantiate Wasm
create parser instance
parse a tiny file
```

For small language tooling, cold start is often more important than hot throughput.

## Required work

### 1. Add a pathological-real fixture

Create a fixture that resembles the grammar that produced the 500 KB Wasm module. If the exact grammar cannot be committed, create a synthetic equivalent that stresses the same dimensions.

Suggested dimensions:

```text
many token regexes
many literal terminals
large DFA
large LR table
many rules with fields
some separated lists
some optional/repeated constructs
at least one realistic small source file
```

Suggested layout:

```text
fixtures/perf/large-runtime/
  grammar.ebnf
  baba.json
  small.input
  medium.input
  large.input
  README.md
```

The README should record why the fixture exists and the original observed failure:

```text
This fixture exists because a real grammar generated about 500 KB of Wasm and took about 6s to instantiate.
```

### 2. Add a benchmark command for generated runtime lifecycle

Add a script such as:

```text
scripts/runtime_bench.ts
```

It should measure separately:

1. compile grammar to bundle;
2. size generated files;
3. write bundle to temp dir;
4. import generated TypeScript runtime;
5. import generated Wasm adapter;
6. compile `WebAssembly.Module` if exposed separately;
7. instantiate Wasm;
8. create parser instance;
9. first parse of small input;
10. second parse of small input;
11. parse medium input;
12. parse large input;
13. validation-only parse if supported later;
14. full-CST parse;
15. memory/pages after repeated parses.

Do not collapse these into one timing. The point is to see where the time goes.

### 3. Report generated artifact sizes by category

For every target and fixture, report:

```text
Tree-sitter grammar.js bytes
query bytes
TypeScript syntax.ts bytes
TypeScript lexer.ts bytes
TypeScript parser.ts bytes
TypeScript mod.ts bytes
Wasm adapter source bytes
embedded Wasm bytes
external parser.wasm bytes
abi.json bytes
parser-kit JSON bytes
parser-kit binary bytes, once available
total generated bytes
largest file
```

### 4. Report plan statistics

For each fixture, report:

```text
token count
literal count
lexer state count
lexer transition count
accept candidate count
LR state count
ACTION entries
GOTO entries
production count
reducer count
field count
branch-conflict count
portable plan JSON bytes
```

These numbers should make it obvious whether size is caused by DFA, LR, debug metadata, generated source boilerplate, or Wasm bytecode.

### 5. Output JSON and text

The command should support:

```sh
deno task bench:runtime
```

and:

```sh
deno task bench:runtime --json runtime-bench.json
```

The JSON shape must be stable enough for CI comparisons:

```json
{
  "fixtures": [
    {
      "name": "large-runtime",
      "targets": {
        "typescript": {
          "generatedBytes": 123456,
          "importMs": 12.3,
          "firstParseMs": 3.4
        },
        "wasm": {
          "generatedBytes": 523000,
          "wasmBytes": 501000,
          "instantiateMs": 6000,
          "firstParseMs": 30.1
        }
      }
    }
  ]
}
```

### 6. Add budget configuration

Add or extend a budget file, for example:

```json
{
  "runtimeBudgets": {
    "large-runtime": {
      "wasmBytesMax": 120000,
      "wasmColdInstantiateMsMax": 500,
      "smallParseMsMax": 10,
      "typescriptGeneratedBytesMax": 80000,
      "portablePlanJsonBytesMax": 100000
    }
  }
}
```

Initially, budgets may be set to current numbers plus slack so CI is not blocked. But record target budgets separately:

```json
{
  "currentBudget": 550000,
  "targetBudget": 50000
}
```

### 7. Add CI mode that does not flake

Wall-clock times are noisy. CI should gate strongly on deterministic size metrics and lightly on timing metrics.

Recommended split:

```text
PR CI:
  - generated bytes
  - plan stats
  - smoke cold-start timing with generous threshold

nightly/manual:
  - detailed timing
  - repeated samples
  - memory/page growth
```

### 8. Add benchmark comparison output

Support comparing two JSON files:

```sh
deno run scripts/runtime_bench.ts --compare before.json after.json
```

Print deltas like:

```text
large-runtime wasm bytes: 501 KB -> 86 KB (-82.8%)
large-runtime instantiate: 6120 ms -> 71 ms (-98.8%)
large-runtime first parse: 31 ms -> 4 ms (-87.1%)
```

## Example benchmark cases

### Tiny grammar

```ebnf
token ID = /[A-Za-z_][A-Za-z0-9_]*/ ;
skip WS = /[ \t\r\n]+/ ;
module = "let" name:ID ;
```

Purpose: baseline overhead. If this emits or loads a large runtime, the architecture is wrong.

### Many literals

```ebnf
module = op* ;
op = "kw0" | "kw1" | "kw2" | ... | "kw500" ;
```

Purpose: literal table pressure.

### Many token regexes

```ebnf
token T0 = /a0[0-9]+/ ;
token T1 = /a1[0-9]+/ ;
...
module = (T0 | T1 | ...)* ;
```

Purpose: DFA/specification pressure.

### Realistic expression grammar

Use arithmetic or JSON-like fixtures.

Purpose: parse loop and CST construction pressure.

### Large application grammar

Use the reported real grammar or a synthetic clone.

Purpose: regression guard for the actual pain.

## Acceptance criteria

- The repo can reproduce and measure cold-start, import, instantiate, parser creation, first parse, and hot parse separately.
- Generated artifact sizes are broken down by file and category.
- The large-runtime fixture exists and is documented.
- JSON benchmark output is stable and machine-readable.
- Budget checks exist and are wired into at least one CI path.
- The script can compare before/after results.
- No runtime architecture changes are made in this task.

## Out of scope

- optimizing the runtime;
- changing output formats;
- changing parser semantics;
- deleting generated files;
- changing default target behavior.
