# Performance Guide

Cold start and hot parse time are different costs. For small CLIs and editor
plugins, the important path is often:

```text
generate or load parser -> import adapter -> create parser -> parse tiny file
```

Use:

```sh
deno task bench:runtime
deno task bench:runtime --json runtime-bench.json
```

The benchmark reports generated bytes, plan statistics, import time, Wasm module
compile time, parser creation, first parse, second parse, and medium/large parse
times for `fixtures/perf/large-runtime`.

`scripts/parser_pipeline_bench.ts` is the parser-v2 benchmark harness. It emits
compact metric names for lexer time, parser construction, validation parse, CST
parse, public tree materialization, emitted bytes, tokens, and plan/node counts.
The `--lexer-only`, `--ast`, `--fixture`, `--budget`, and `--json` flags match
the parser-v2 budget entries in `size-budgets.json`.

Parser-v2 task fixtures live under `fixtures/perf/parser-v2/` and can be run
directly:

```sh
deno run --allow-read --allow-write --allow-run scripts/parser_pipeline_bench.ts --fixtures-root fixtures/perf/parser-v2 --fixture tiny-dsl --cst --json parser-v2-tiny-dsl.json
```

The final parser-v2 gate is:

```sh
deno run --allow-read --allow-write scripts/parser_pipeline_bench.ts --budget size-budgets.json --json tmp/parser-v2-cutover.json
```

It reports separate lexer, parser construction, validation parse, CST parse, AST
materialization, generated-size, token-count, CST-node, and plan-size metrics.
`size-budgets.json` also contains a `parserV2` section with the small-plan,
parser-create, validation, CST, lexer-throughput, and incremental single-edit
targets used to review future tightening.

Wasm can be slower for small inputs because module setup, source copying, and
JavaScript result materialization can dominate table execution. Prefer the
shared TypeScript runtime for small and first parses. Use Wasm when the input is
large enough or repeated enough to amortize startup, and keep Wasm creation
explicit and async where possible.

Budgets live in `size-budgets.json`. Current budgets keep CI stable; target
budgets record the intended slim-runtime numbers.

Compare two benchmark JSON files with:

```sh
deno run --allow-read scripts/runtime_bench.ts --compare before.json after.json
```

Inspect a generated binary parser plan with:

```sh
deno task inspect-plan generated/wasm/parser.plan
```
