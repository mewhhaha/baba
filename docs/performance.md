# Performance Guide

Cold start and hot parse time are different costs. For small CLIs and editor
plugins, the important path is often:

```text
generate or load parser -> import adapter -> create parser -> parse tiny file
```

Use:

```sh
deno task bench:runtime
deno task bench:runtime --json runtime-bench.json
```

The benchmark reports generated bytes, plan statistics, import time, Wasm module
compile time, parser creation, lazy lex tape time, Wasm trace validation, cursor
parse time, and throughput ratios for the runtime fixtures.

Wasm can be slower for small inputs because module setup and source copying can
dominate table execution. The generated Wasm API keeps hot paths cursor-first:
`parse()` returns cursor wrappers, `validate()` uses a Wasm trace, and `lex()`
returns a lazy token tape. Measure those surfaces separately before optimizing a
caller.

The most relevant runtime benchmark fields are:

- `lexTapeSmallMs` and `lexTapeMediumMs`;
- `validateTraceSmallMs` and `validateTraceMediumMs`;
- `cursorParseFirstMs`, `cursorParseSecondMs`, `cursorParseMediumMs`, and
  `cursorParseLargeMs`;
- `compileModuleMs`;
- `createParserMs`;
- `generatedBytes`;
- `planStats`;
- `artifactSizes.corePlanBinaryBytes`;
- `artifactSizes.runtimeMetadataBinaryBytes`.

Budgets live in `size-budgets.json`.

Compare two benchmark JSON files with:

```sh
deno run --allow-read scripts/runtime_bench.ts --compare before.json after.json
```

Inspect a generated binary parser plan with:

```sh
deno task inspect-plan generated/wasm/parser.plan
```
